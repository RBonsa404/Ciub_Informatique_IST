0. Règles de lecture et décisions d’architecture
Ce document transforme les éléments fournis dans les trois sources en unités de travail codables.
Deux catégories sont utilisées :
Source
 : élément explicitement présent dans les documents fournis.
Décision d’implémentation
 : détail ajouté pour rendre le système directement codable lorsque le cahier des charges ou les diagrammes n’imposent pas la forme technique exacte.
Les URI REST, le nommage exact des packages, la structure des DTO et certains champs techniques ne sont pas explicitement définis par les diagrammes de séquence. Ils sont donc proposés ici comme 
contrat d’implémentation à figer une fois au démarrage
, sans modifier les flux fonctionnels UML.

1.5 Principes non négociables
Aucun accès direct à la base depuis un Controller.
Aucune Entity JPA exposée directement par l’API.
Tous les endpoints écrivent/lisent via DTO.
Toute règle métier appartient au Service.
Toute validation d’autorisation serveur est indépendante des Guards Angular.
Les erreurs API utilisent un format unique.
Toute donnée sensible est absente des réponses publiques.
Les listes volumineuses sont paginées.
Les transitions d’état sont contrôlées côté serveur.
Les opérations d’inscription concurrentes utilisent une stratégie transactionnelle empêchant le dépassement de capacité.

SECTION 3 — CONTRATS D’INTERFACES ET SPÉCIFICATION API / DTO
3.1 Convention générale API
Préfixe :
/api/v1
Format d’erreur :
{
  "timestamp": "2026-09-07T16:00:00Z",
  "status": 400,
  "code": "VALIDATION_ERROR",
  "message": "Les données fournies sont invalides",
  "path": "/api/v1/inscriptions",
  "details": [
    {
      "field": "sessionId",
      "message": "La session est obligatoire"
    }
  ]
}
Codes :
200
 : opération de lecture ou de modification terminée.
201
 : création terminée.
400
 : validation métier ou syntaxique invalide.
401
 : non authentifié.
403
 : authentifié mais non autorisé.
404
 : ressource inexistante.
409
 : conflit métier, par exemple doublon ou capacité atteinte.
500
 : erreur inattendue.
Le cahier des charges impose explicitement la protection RBAC de chaque endpoint, le bcrypt, le 2FA des comptes concernés, la journalisation des connexions et des actions sensibles.

ANNEXE C — RÈGLES D’INTÉGRATION ENTRE MEMBRES
Un contrat DTO consommé par un autre module ne doit pas être modifié sans Pull Request de coordination.
Une migration qui ajoute/modifie une FK doit être validée avec le module propriétaire de la table référencée.
Un endpoint protégé doit documenter la permission attendue.
Les composants frontend communs doivent rester dans 
shared/
.
Les fonctions transverses doivent rester dans 
core/
.
Les notifications inter-modules doivent passer par 
NotificationService
, jamais par insertion SQL directe dans les autres services.
Les tests des parcours critiques doivent être exécutables sur une base de test reproductible.
Toute modification du modèle UML après le début du codage doit être accompagnée du changement SQL et DTO correspondant.
Conclusion opérationnelle
Le projet peut démarrer le codage sur cette base en conservant les classes et flux fournis, tout en traitant explicitement les écarts fonctionnels : notamment les données de profil demandées par le cahier des charges mais absentes de 
Utilisateur
, ainsi que la notion de proposition absente du diagramme de classes.
L’ordre de démarrage recommandé est :
1. OUARE : squelette dépôt / CI / PostgreSQL
2. PAMOUSSO : Utilisateur / Role / Permission / Security
3. BONSA + SALOU : événements / formations / inscriptions
4. KI : actualités / projets / contact
5. ZONGO : notifications / dashboard
6. Tous : frontend, intégration, tests
7. OUARE : sécurité, performance, déploiement
Cette séquence minimise les blocages tout en conservant des branches fonctionnelles indépendantes et des contrats d’API suffisamment stables pour permettre un développement parallèle.
